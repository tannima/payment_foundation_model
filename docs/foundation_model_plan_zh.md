# 信用卡支付风险基座模型方案

## 1. 背景

现有信用卡支付风控建模体系主要依赖实时特征平台预先构造 `velocity` 类特征，再使用二分类模型进行训练和推理。

典型流程如下：

1. 在实时特征平台中配置特征，主要形式为 `主体#客体#过滤条件#时间窗口#计算函数`
2. 从历史样本中离线计算特征值，并结合标签 `label` 训练二分类模型

以“用户 3 天内换卡次数”为例，特征配置为：

- `user_id#card_no#payment#3 days#count distinct`

其本质是：

- 按 `user_id` 检索历史交易
- 根据过滤条件筛选交易
- 对 `card_no` 做 `count distinct`

这种范式在单业务场景下是有效的，但存在明显瓶颈：

- 输入依赖人工定义特征，跨业务域难以对齐
- 模型学习的是人工压缩后的统计量，Scaling 上限较低
- 新业务接入需要在实时特征平台新增大量特征，工程成本高
- 不同业务标签逻辑不同，统一二分类训练容易互相干扰

过去的实验已经说明：

- 样本量增大明显有效
- 参数量在中小规模内有效
- 但在“固定 tabular 数值特征 + 二分类任务”的范式下，参数扩展到几十 Million 后收益开始明显变缓

这说明问题不在模型结构本身，而在于输入信息和训练目标对大模型来说过于简单。

---

## 2. 目标

下一代风险基座模型的目标不是简单替换现有 XGB 或 FT-Transformer，而是构建一个真正可扩展、可跨业务迁移、可支持多任务的 `Transaction Foundation Model`。

核心目标包括：

1. 使用统一的原始风控事件作为输入，而不是预先计算好的数值特征
2. 通过历史相关事件上下文替代人工 velocity 特征
3. 学习跨业务共享的风险语义表征，而不是单一业务标签
4. 通过更大的样本量、参数量和更丰富训练任务提升模型上限
5. 支持风险分类、支付联合决策、语言任务等多种下游任务

一句话定义：

- 构建一个基于原始交易事件序列、支持多实体关系建模、以多任务预训练为核心的支付风险基座模型

---

## 3. 总体设计思路

整体方案分为六层：

1. 统一事件 Schema
2. 上下文检索与组装
3. 事件级编码
4. 序列与关系增强 Transformer 主干
5. 多任务预训练
6. 多业务后训练与在线推理

整体数据流如下：

1. 当前交易到达
2. 抽取 anchor 实体，如 `user_id/card_no/device_id/bill_email/bill_address/ip`
3. 从事件数据库中检索与这些实体相关的历史事件
4. 去重、排序、裁剪，组装成标准化上下文
5. 输入基座模型，得到 `foundation embedding + risk score`
6. 下游业务 head 结合域内特征完成最终决策

---

## 4. 输入表示：统一使用原始事件属性

### 4.1 为什么要从数值特征切换到原始事件

原始事件输入的核心优势有三点：

1. 所有业务域都可以映射到统一 schema，天然支持跨场景
2. 不再依赖上千个预定义实时特征，降低新业务接入成本
3. 模型可直接学习“行为过程”和“关系变化”，而不是只学习最终统计值

### 4.2 统一 Schema 建议

每一笔交易统一映射为标准事件对象，包含以下字段组：

- 时间类：`gmt_occur`、相对 anchor 的时间差
- 金额类：`event_amount`
- 用户类：`user_id`
- 卡类：`card_no`、`card_bin`、`issuer`、`card_country`
- 设备网络类：`device_id`、`ip_address`、`ip_country`
- 账单类：`bill_email`、`bill_address`
- 商品类：`item_name`、商品类目
- 决策结果类：`is_reject`、`is_3ds`、`is_approve`、`is_success`
- 事后标签类：`is_fraud`、`is_cb`
- 业务域类：`business_domain`
- 缺失标记：字段缺失 / 不适用 / 未采集

标准化原则：

- 缺失必须显式编码
- 数值和时间使用统一分桶和归一化规则
- 地址、商品名等文本字段保留原始值和规范化结果
- 域内特有字段单独保存在扩展区域，不直接污染主干输入

---

## 5. 上下文检索：用历史事件替代 velocity 特征

### 5.1 核心思想

不再实时计算某个 `count distinct` 值，而是实时检索和当前交易最相关的历史事件，让模型自己从上下文中学习：

- 近 1 天交易次数
- 近 7 天换卡次数
- 设备共享关系
- 地址切换行为
- 突然高频爆发等模式

### 5.2 检索维度

围绕当前交易并行按以下实体召回：

- `user_id`
- `card_no`
- `device_id`
- `bill_email`
- `bill_address`
- `ip_address`
- 可扩展：`card_bin`、手机号、merchant 等

### 5.3 检索预算

建议首版采用固定召回预算：

- 用户最近 50 笔
- 卡最近 30 笔
- 设备最近 30 笔
- 邮箱最近 20 笔
- 地址最近 20 笔
- IP 最近 20 笔

去重后保留约 `100~300` 笔事件。

### 5.4 裁剪与保留原则

不能只保留最近事件，还要保留信息量高的事件，例如：

- 新卡首次出现
- 同设备不同卡
- 同地址不同用户
- 同卡跨国家 / 跨 IP
- 短时间内大额连续交易

本质上，这一步是用“上下文召回”替代“人工聚合特征”。

---

## 6. 高基数 ID 的建模方式

`card_no/user_id/device_id` 等高基数 ID 是核心难点。

不能简单做静态词表 embedding，原因如下：

- 词表会极大
- 新 ID 会产生 OOV
- 模型会把大量参数浪费在记忆单个 ID 上

建议使用三层并行编码。

### 6.1 局部重编号

在单个样本上下文内部，对实体重新编号：

- `card_1/card_2/card_3`
- `device_1/device_2`
- `email_1/email_2`

作用：

- 保留“是否同一实体”
- 支持模型学习 `count distinct`
- 避免 OOV

这是学习“换卡次数”“共享设备数”的关键归纳偏置。

### 6.2 多哈希桶嵌入

对原始高基数 ID 做多路哈希映射：

- 多个 hash function
- 固定大小桶
- embedding 求和或拼接

作用：

- 保留弱全局身份记忆
- 新 ID 可编码
- 避免超大词表

### 6.3 角色型特征

高基数 ID 更重要的是它在当前上下文中的角色，而不是字符串本身。

建议显式编码：

- 是否首次出现
- 距上次出现多久
- 在窗口内出现次数
- 是否与 anchor 相同
- 是否是切换点

## 7. 模型主干设计

### 7.1 设计原则

不建议直接把结构化字段拼成文本再送进标准 LLM。

更合理的方案是构建层次化的 `Transaction Transformer`，同时利用：

- 事件序列信息
- 实体关系信息
- 时间变化信息
- 当前交易与历史交易的匹配关系

### 7.2 模型结构

建议分为四层：

1. 字段编码层
2. 事件编码层
3. 关系增强层
4. 序列主干层

### 7.3 字段编码层

不同字段采用不同编码器：

- 低基数类别：embedding
- 数值字段：分桶 embedding + 连续值投影
- 时间字段：绝对时间编码 + 相对时间编码
- 文本字段：子词编码器或轻量 text encoder
- 高基数 ID：局部编号 embedding + 哈希 embedding + 角色 embedding

### 7.4 事件编码层

将一笔交易的多字段先压缩为少量 event token，例如：

- identity token
- payment token
- network token
- item token

或者进一步压缩为一个事件表示。

这样可以避免 200 笔交易膨胀为上万 token。

### 7.5 关系增强层

建议在 attention 中引入 typed relation bias：

- same user
- same card
- same card_bin
- same device
- same email
- same address
- same ip
- 时间差 bucket
- 新实体切换标记

这样模型会天然关注真正重要的互累关系。

### 7.6 实体记忆层

建议为每类实体增加 memory token：

- card memory
- device memory
- email memory
- address memory
- ip memory

事件 token 和实体 token 双向交互，使模型显式聚合某张卡或某设备的局部行为摘要。

这一步相当于将过去手工 velocity 中的“统计对象”结构化显式化。

### 7.7 注意力机制

由于上下文较长，不建议纯 dense attention。

推荐混合注意力：

- 最近事件用 dense attention
- 远期事件用 block sparse attention
- anchor 对全部事件做全局 attention
- 同实体事件之间建立 relation shortcut

---

## 8. 为什么这套结构能学习 velocity

过去 velocity 特征做的事情，本质上只有两类：

1. 局部集合统计，如 `count / count distinct / sum / recency`
2. 跨实体关系变化，如换卡、换设备、共享地址、高频爆发

新的模型结构对这两类能力都有直接支持：

- 局部重编号和实体 token 支持 `count distinct`
- 时间差编码支持不同时间窗口
- 关系 attention 支持不同过滤条件
- 历史上下文支持 burst 和切换模式学习

因此，模型学习的不再是某个单独 velocity 数值，而是更底层的风险行为过程表征。

## 9. 预训练任务设计

预训练建议分阶段推进。

### 9.1 第一类：风险原子任务

目标是先让模型学会过去 velocity 特征描述的统计规律。

建议预测以下原子量：

- `count`
- `count distinct`
- `sum(amount)`
- `max(amount)`
- `avg(amount)`
- `time since last occurrence`
- `new entity appeared`
- `switch happened`
- `burst score in 1h/1d/7d`

训练形式可以结合：

- 回归
- 分桶分类
- 排序损失

不建议直接把几千个 velocity 名称硬编码成几千个头，而应抽象成更基础的原子算子。

### 9.2 第二类：事件结果自回归预测

目标是学习支付流程中的因果决策链，而不是把多个结果字段当作彼此独立的并行分类头。

支付链路天然存在前后依赖关系：

- 只有风控不拒绝，后续银行决策才会发生
- 只有风控和银行都未拒绝，且支付结果成功，后续才可能产生 `is_fraud`、`is_cb`

因此建议使用自回归方式建模结果序列，让模型按事件发生顺序逐步预测：

1. 风控决策，如 `is_reject`、`is_3ds`
2. 银行决策，如 `is_approve`
3. 支付结果，如 `is_success`
4. 事后风险结果，如 `is_fraud`、`is_cb`
5. 可扩展：拒绝码、风险原因码、处置动作等

训练方式上，可将结构化事件上下文编码为条件前缀，再追加决策链 token 序列，使用 teacher forcing 做自回归训练。

这类设计的好处是：

- 天然满足支付链路中的条件因果关系
- 避免把本不该同时出现的结果标签硬性并列建模
- 让模型学习“某一步发生后，后续还会发生什么”的过程知识

### 9.3 第三类：去噪与缺失鲁棒性任务

目标是提升跨业务迁移能力。

建议包括：

- mask 部分字段并恢复
- 删除部分历史事件后恢复关系
- 模拟不同业务域字段缺失
- 同一风险模式跨域对比学习

这一步直接用于缓解不同业务字段覆盖不一致的问题。

### 9.4 第四类：语言任务

这是更长期方向。

在结构化输入后拼接自然语言问题，如：

- “是否存在躲闪行为？”
- “这笔交易的高风险原因是什么？”

让模型生成文本回答，实现风险分析能力和结构化输入到文本空间的对齐。

现阶段不建议优先投入，应在前述任务验证成功后再推进。

## 10. 后训练设计

后训练不建议把所有业务的标签硬并成一个统一二分类任务。

更合理的形式是：

- 共享 backbone
- 每个业务一个独立 head
- 每个业务可拼接自己的已有特征
- 每个业务单独校准阈值和风险水位

也就是说：

- 基座模型负责学习通用风险语义
- 业务 head 负责把风险语义映射到各自的标签定义和决策边界

这种方式的好处是：

- 充分利用历史业务资产
- 降低不同标签定义互相污染的风险
- 更容易在现网逐步替换和融合

---

## 11. 在线系统设计

### 11.1 从特征平台升级为上下文平台

在线系统的核心不是实时算聚合特征，而是实时组装与当前交易相关的事件上下文。

在线链路建议如下：

1. 当前交易进入系统
2. 抽取 anchor 实体
3. 并行检索相关历史事件 ID
4. 拉取事件明细
5. 去重、排序、裁剪、加关系标记
6. 送入模型推理
7. 输出 foundation embedding 和风险分

### 11.2 存储设计

建议拆为两类核心存储：

- `entity -> recent event ids` 的倒排索引
- `event_id -> event blob` 的事件明细存储

可选实现：

- 热层：Redis / RocksDB
- 温层：HBase / Cassandra / Bigtable
- 冷层：离线数据湖

### 11.3 延迟预算

首版建议将 P99 控制在大致如下范围：

- 实体抽取：`<1 ms`
- posting list 查询：`5~10 ms`
- event blob 拉取：`5~10 ms`
- 裁剪组装：`2~5 ms`
- online student 推理：`15~40 ms`

总耗时目标：

- `30~60 ms`

### 11.4 Train-Serve 一致性

必须保证训练和线上共用：

- 同一 schema
- 同一规范化逻辑
- 同一检索预算
- 同一局部编号逻辑
- 同一裁剪规则

否则很容易出现严重的训练-服务偏移。

## 12. 规模路线与 7B 的现实路径

虽然长期目标可以是 7B，但工程上不建议一开始就直接用 7B 做线上主模型。

更现实的路线是：

1. 先训练 `100M~300M` 原型，验证输入范式是否有效
2. 再训练 `300M~1B` backbone，验证多任务预训练和多域迁移收益
3. 再训练 `1B~3B` 或更大的 teacher 模型
4. 将 teacher 蒸馏到 `100M~500M` student 用于在线全量
5. 更大模型保留给离线打分、灰度流量、疑难样本复判和分析任务

否则即使离线指标很好，线上延迟和成本也可能无法接受。

---

## 13. 推荐实验路线

建议按四个阶段推进。

### 阶段一：验证输入范式

目标：

- 原始事件上下文是否优于预计算特征输入

做法：

- 训练 `100M~300M` 级别原型
- 任务先只做风险原子任务和结果预测
- 与 XGB / FT-Transformer 做离线对比

### 阶段二：验证结构收益

建议做以下 ablation：

- 无局部重编号 vs 有局部重编号
- 无实体记忆 token vs 有实体记忆 token
- 纯序列 attention vs 关系增强 attention
- 只用最近事件 vs 检索增强上下文

目标：

- 证明模型确实学到了 velocity 替代能力

### 阶段三：验证多域迁移

做法：

- 单域训练
- 多域混训
- 多域预训练 + 单域后训练
- 模拟字段缺失

目标：

- 证明统一基座在跨业务迁移上的收益

### 阶段四：验证 scaling law

做法：

- 多参数规模实验
- 多样本规模实验
- 对比原子任务和下游任务收益曲线

目标：

- 判断是否具备继续推大到 7B 的价值

---

## 14. 当前阶段最重要的三件事

如果现在开始落地，这三件事优先级最高：

1. 定义统一 schema 和 context 组装协议
2. 训练一个能学习 `count distinct / switch / burst` 的原型主干
3. 建立多业务预训练 + 多 head 后训练的实验闭环

这三件事跑通之后，才能判断是否值得继续做更大规模投资。

---

## 15. 结论

这一方案与传统 tabular 风控模型的根本区别在于：

- 输入不再是人工聚合后的统计值，而是原始事件序列与关系
- 模型不再只学“是否欺诈”，而是学习可迁移的风险行为语义
- 系统不再围绕“查特征值”构建，而是围绕“检索上下文并推理”构建

如果方案做成，它带来的价值包括：

1. 更强的跨业务泛化能力
2. 更多任务类型支持，如风险分类、联合决策、语言推理
3. 更高的参数扩展上限
4. 更低的新业务接入和特征工程成本

真正要让 7B 参数有意义，参数里承载的不能只是某几个 velocity 数值，而应该是：

- 风险行为过程
- 实体关系变化
- 跨时间尺度的异常模式
- 跨业务共享的风险语义

这也是风险基座模型与传统特征模型最本质的区别。
