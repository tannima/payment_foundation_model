# 信用卡支付风险基座模型在线服务设计

## 1. 目标

本设计文档聚焦在线系统实现，回答三个问题：

1. 与当前交易相关的上下文事件如何实时检索
2. 如何在延迟约束下组装模型输入
3. 基座模型如何与线上风控链路集成

在线系统的核心不是“实时计算聚合值”，而是“实时检索并组装高信息量事件上下文”。

---

## 2. 在线系统职责

`Context Engine` 负责完成以下工作：

1. 从当前交易中抽取 anchor 实体
2. 按实体召回相关历史事件
3. 拉取事件明细并做去重
4. 按时间和关系重要性组装上下文
5. 输出模型可直接消费的结构化张量

它本质上是下一代实时特征平台的核心能力。

---

## 3. 在线链路

建议在线推理链路如下：

1. 当前交易到达
2. 字段标准化和实体抽取
3. 并行查询实体倒排索引
4. 合并得到候选历史事件 ID
5. 拉取事件明细
6. 去重、排序、裁剪、局部实体重编号
7. 生成模型输入
8. 模型输出 `foundation embedding + risk score`
9. 下游业务 head、规则引擎或决策引擎给出最终动作

---

## 4. 存储设计

建议至少拆成三张逻辑表。

### 4.1 事件明细表

用途：

- 存储标准化后的完整事件内容

逻辑形式：

- key: `event_id`
- value: event blob

内容包括：

- 所有标准 schema 字段
- 规范化后的地址、邮箱、商品类目等
- 业务域
- 当时可见的决策结果
- 可异步补充的事后标签

### 4.2 实体倒排索引表

用途：

- 按实体快速找到相关历史事件

逻辑形式：

- key: `entity_type#entity_value`
- value: 按时间倒序排列的 recent event id list

例如：

- `card#hash_xxx -> [eid_1001, eid_998, eid_970, ...]`
- `device#dev_xxx -> [eid_1102, eid_1097, ...]`

### 4.3 事件实体映射表

用途：

- 记录一笔事件涉及哪些实体
- 支持回溯、校验、离线生成和调试

逻辑形式：

- key: `event_id`
- value: entity list

---

## 5. 存储分层建议

建议采用冷热分层：

- 热层：Redis / Aerospike / RocksDB，保存最近高频实体 posting list
- 温层：HBase / Cassandra / Bigtable，保存长窗口 posting list 和 event blob
- 冷层：离线数仓 / 湖仓，供训练和回放使用

这样设计的原因是：

- 支付风控高度依赖最近事件
- 热数据命中率会显著影响在线延迟
- 长窗口数据量大，不适合完全放在内存中

---

## 6. 检索策略

### 6.1 并行召回

围绕当前交易并行按实体召回：

- `user_id`
- `card_no`
- `device_id`
- `bill_email`
- `bill_address`
- `ip_address`
- 可扩展：`card_bin`、手机号、merchant

### 6.2 首版预算

推荐首版预算如下：

- user: 50
- card: 30
- device: 30
- email: 20
- address: 20
- ip: 20

合并去重后形成 `100~300` 条候选事件。

### 6.3 候选事件排序

不能只按时间近远排序，建议增加启发式 rerank 分数：

```text
score(event) =
  w1 * recency_score
+ w2 * same_card
+ w3 * same_device
+ w4 * same_email
+ w5 * same_address
+ w6 * same_ip
+ w7 * amount_anomaly
+ w8 * new_entity_transition
```

保留原则：

- 最近若干事件强制保留
- 强关系事件保底保留
- 避免同一实体链上过多重复低信息事件挤占预算

---

## 7. 上下文组装

组装输出建议包括：

- anchor event
- 历史 event sequence
- relation-to-anchor 标记
- 局部实体编号
- 缺失字段标记
- 相对时间编码

第一阶段可不引入显式 entity memory token，由模型离线先验证有效性。

后续升级时，可在组装阶段增加：

- card memory token
- device memory token
- email memory token
- address memory token

---

## 8. 实时局部实体编号

局部实体编号是线上组装逻辑的关键步骤。

流程如下：

1. 对召回后的候选事件去重
2. 在单样本内收集唯一实体值
3. 分别按实体类型映射为局部编号
4. 对每个事件写入 `local_id`

例如：

- 样本内出现两张卡，则映射为 `card_1/card_2`
- 出现三个 IP，则映射为 `ip_1/ip_2/ip_3`

这一步必须与离线训练完全一致，否则模型线上会退化。

---

## 9. 在线延迟预算

建议把 P99 延迟预算控制在：

- 标准化与实体抽取：`<1 ms`
- posting list 查询：`5~10 ms`
- event blob 拉取：`5~10 ms`
- 去重与组装：`2~5 ms`
- student 模型推理：`15~40 ms`

总延迟目标：

- `30~60 ms`

如果后续需要引入更大 teacher 模型，建议只用于：

- 离线打分
- 小流量复判
- 高风险疑难样本二阶段判断

不建议一开始直接用于全量同步在线推理。

---

## 10. 缓存设计

建议至少两级缓存。

### 10.1 posting list cache

缓存高频实体最近 posting list，适用于：

- 被连续尝试盗刷的卡
- 高频共享设备
- 高频共享 IP

### 10.2 assembled context cache

缓存部分已组装上下文，适用于：

- 同一张卡或设备在短时间内重复触发推理
- 短时间内上下文变化不大

此类缓存可显著降低重复组装成本，但要谨慎控制失效策略。

---

## 11. 新鲜度与一致性

支付风控对事件新鲜度要求高，因此建议：

- 最新事件先进入流式日志
- 热层 posting list 毫秒级或秒级更新
- event blob 可先写核心字段，再异步补齐弱依赖字段
- 事后标签单独异步回流，不进入实时决策输入

尤其要注意：

- `is_fraud/is_cb` 是监督信号，不应作为实时输入

---

## 12. 与现有系统的集成方式

首版不建议完全替换现有风控系统。

推荐集成方式：

1. 当前实时特征平台继续保留
2. 新增 context engine 和 foundation model
3. foundation model 输出一个或多个 embedding 与风险分
4. 这些输出与现有业务特征拼接，进入业务域 head 或规则系统

这样做的优点：

- 可渐进灰度
- 出问题时易回退
- 更容易验证增量收益

---

## 13. 首版落地边界

第一阶段在线原型建议控制范围：

1. 先支持 `user/card/device/email/ip` 五类实体
2. 每样本最多 `128~256` 个 event
3. 先使用 `100M~500M` online student
4. 只输出基础 risk score 和 embedding
5. 暂不在在线链路上加入复杂语言任务

---

## 14. 结论

在线服务体系的核心转变是：

- 从“查聚合特征值”升级为“检索上下文并推理”

这要求线上系统从特征平台思维切换到上下文平台思维。

真正需要建设的能力不再只是：

- 某个 key 在 7 天内出现了几次

而是：

- 当前交易与哪些历史事件有关
- 哪些历史关系最值得模型看见
- 如何在延迟约束内把最有信息量的上下文交给模型

这将决定风险基座模型能否真正在线落地。
